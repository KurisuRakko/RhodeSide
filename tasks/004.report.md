1. **中** · `macos/Sources/Rhodeside/RemoteUpdater.swift:108-111, 96-97, 159, 169-171`
   热更新「失败一次就永久不再自动重试，且错误提示 5 秒后被抹掉」。
   触发场景：清单拿到了但内容不能用（`verify` 失败 / `bridge` 不一致 / 下载后 sha256 或 size 不符，`RemoteUpdater.swift:159,160-162,169-171`）。
   代码：失败时把清单 ETag 记下来——
   ```swift
   case .failed(let msg, let tag):
       if let tag { etag = tag }
       lastError = msg
   ```
   下一次定时 `check()` 会带上 `If-None-Match`，nginx 因为清单没变回 304，于是：
   ```swift
   case .notModified:
       lastError = nil
   ```
   为什么错：`.failed(_, etag:)` 的注释本意是「清单没变就不重复下载包」，但它同时把 `etag` 设成了**不可用清单**的 ETag，而 `run` 只有在清单内容变化时才会重新进入下载分支。结果是：一次瞬时/可恢复的失败（例如包下载损坏、或 `bridge` 没对上）之后，自动检查永远 304，既不重试也不报警；随后 `.notModified` 又把 `lastError` 清成 nil，设置页的「前端更新」只剩一行正常的「检查于 …」，用户完全看不出更新其实已经停了。只有点「立即检查」（`force: true` → `etag = nil`）才能恢复。对比：真正抛错的路径（HTTP 失败，`RemoteUpdater.swift:153-156`）因为 `check` 的 catch 传 `etag: nil` 反而是会重试的，说明这是失败分支之间的语义混淆。

2. **中** · `macos/scripts/deploy.sh:78`
   `mac:test` 会在单元测试失败时仍然返回 0。
   触发场景：在 rakkoserver 上 `corepack pnpm mac:test`（或 `deploy.sh test`），Mac 上 `swift test` 有失败用例。
   代码：
   ```bash
   ssh "$MAC" "cd $REMOTE/macos && swift test 2>&1 | tail -n 60"
   ```
   为什么错：`ssh mac "cmd"` 由远端**登录 shell（zsh）**执行；zsh 默认不开 `pipefail`，管道的退出码是最后一条命令 `tail` 的（0）。本地 `set -euo pipefail` 管不到远端管道。于是 `swift test` 即使 exit 1，ssh 也返回 0，本地脚本静默通过。`build-app.sh:10-15` 对同一陷阱专门用 `PIPESTATUS` 兜了底，这里漏了；应改成 `set -o pipefail; swift test 2>&1 | tail -n 60`（或 `swift test; rc=$?; ...`）。

3. **中** · `web/src/settings/Settings.tsx:260-262, 302`
   切换「时装」时把**旧时装的模型组**一起写回，导致模型组 Select 的 `value` 不在 options 里，而且持久化了一个新时装并不存在的组。
   触发场景：同一模型下有两套时装，各自支持的组不同（例如 A 有 `正面/基建`，B 只有 `正面`）。在 A 上选中 `基建`，再把「时装」切到 B。
   代码：
   ```tsx
   const groups = sets.filter((s) => s.outfit === outfit).map((s) => s.group)
   const group = pet.group ?? current?.group ?? (...)
   ...
   <Pick label="时装" value={outfit} options={outfits.map(...)}
         onChange={(v) => patch({ outfit: v, group: group })} />
   ```
   `onChange` 里捕获的 `group` 是本帧用**旧 `outfit`** 算出来的；切到 B 后 `patch({outfit: v, group: '基建'})` 被原生合并、写进 `config.json`。下一页 `groups` 按 B 重算为 `['正面']`，而 `pet.group` 已是 `'基建'`，`<Pick value={group}>` 的 value 不在 items 里（Base UI 会退化成占位），同时原生把 `group: '基建'` 发给桌宠页，而桌宠页在 B 里找不到该组只能回退 正面/基建——界面显示的和实际跑的不一致。切时装时应只改 `outfit`（或同时把 `group` 收敛到新时装的第一个组），别把旧组带上。

4. **中** · `macos/scripts/deploy.sh:48-56`
   全量部署先发布前端、再编译原生；编译失败时前端已经上线。
   触发场景：改了 `web/`（没改协议版本）又顺手改了 Swift，`deploy.sh full` 里 `publish_web` 成功后 `build-app.sh` 的 `swift build` 失败。
   代码：
   ```bash
   full)
     build_web
     publish_web          # 先把新前端推到公网通道
     ...
     ssh "$MAC" "bash $REMOTE/macos/scripts/build-app.sh"
   ```
   为什么错：脚本退出，但公网清单的构建号已经比 Mac 上正在跑的 App 新；正在运行的 App 会在 5 秒内验签通过并热更新到新前端，而它依赖的原生改动还没进二进制。`bridge` 只能挡住作者记得手动 +1 的协议变更，挡不住普通行为改动。至少应把 `publish_web` 挪到 `build-app.sh` 成功之后（或者在 full 里默认不 publish，另跑 `web`）。

5. **轻** · `macos/Sources/Rhodeside/PetManager.swift:47-50, 311, 316` + `RemoteUpdater.swift:196-197`
   远程更新装完后可能连着重载两次页面。
   触发场景：远程包较大或磁盘慢，`install` 的 `move web-dev → web-dev.replaced` / `move web-dev.incoming → web-dev` 产生的 FSEvents 回调先于 `finish` 到达主线程。
   代码：`filesChanged` 只看事件发生当刻的标志——
   ```swift
   if web, CACurrentMediaTime() < ignoreWebEventsUntil { web = false }
   if web { webDebounce.call { ... reloadWeb ... } }
   ```
   `ignoreWebEventsUntil` 是 `onApplied` 里才设的；事件若先到，会排一个 0.4s 的 debounce，`onApplied` 随后的 `reloadWeb` 并不会取消它，于是再重载一次。触发后表现为页面闪一下/白一帧（桌宠位置不受影响）。修法是在 `reloadWeb` 里也 `webDebounce.cancel()`，或让 `install` 期间的路径全部落在跳过名单里。

6. **轻** · `macos/Sources/Rhodeside/Pet.swift:282-299` + `web/src/pet/main.ts:275-284`
   点击穿透的「身上」判定用的是最多 100ms 前的包围盒，走路时小人前缘会有几个 pt 点不到。
   触发场景：把步速调到快/大（如高度 210、步速 1.4，步速公式 `height*0.42*stride` ≈ 123pt/s），在小人朝自己走来的前缘按下。
   代码：网页只在 `now - lastBounds >= 100` 时发一次——
   ```ts
   if (native && now - lastBounds >= 100) { lastBounds = now; ... post({type:'bounds', ...}) }
   ```
   原生用这个 `bounds` 决定要不要向网页发 `hit`：
   ```swift
   if b.insetBy(dx: -4, dy: -4).contains(local) { ... send hit ... }
   ```
   100ms 内小人前进约 5–12pt，只有 4pt 的 inset 兜底，超出的前缘鼠标根本不会进 `hit` 流程，窗口保持 `ignoresMouseEvents = true`，点击穿到下面的窗口。数据并不难拿（`bounds` 可以由原生按 `pos + vx` 自己外推，或提高到 30Hz），目前是纯逻辑上的漏判。

12. **轻** · `web/src/stage/model.ts:210` 与 `macos/Sources/PetCore/Brain.swift:336-344`
    落地的 x 在窗口平台上不做横向夹取，只靠下落过滤保证落在段内。
    `fall` 用 `$0.segment.contains(x: nx, tolerance: 0)` 选平台后 `land(on:x:)` 对 `.ground` 才 `clamp`，对 `.window` 不夹。当前逻辑下 `nx` 确实在段内所以安全，但如果两帧之间平台列表被后台扫描换成更短的段（被别的窗口挡住），`land` 会把脚放在段外，下一帧 `stand` 找不到包含脚的段 → `startFall` → 再落地，可能连续抖动一小段。证据强度一般，列在这里是因为它正好是任务点到的「落地 x 越界」路径。

13. **轻** · `macos/Sources/Rhodeside/Debug.swift:17` + `Pet.swift:362-366`
    `rhodeside://debug/eval?js=…` 会无条件把任意 JS 注入每只桌宠页面。任何本机进程都能用 `open` 调这个 URL。桌宠页的 `webkit.messageHandlers.rhodeside` 只支持 `load/play/hit/snapshot/log` 这类消息，改不了配置，所以危害有限；但它是一个不需要任何鉴权的脚本执行面，且 `js` 直接来自 URL query（`URLComponents` 只是百分号解码）。个人自用可接受，写出来是因为它和热更新的信任模型放在一起看值得一提。

14. **轻** · `macos/Sources/Rhodeside/RemoteUpdater.swift:184-194`
    解压用 `/usr/bin/tar -xzf archive -C incoming`，没有 `--no-absolute-names`/路径与符号链接加固，之后只检查 `pet.html`、`settings.html` 存在。当前唯一的防线是「包内容必须匹配签名 payload 里的 sha256」，所以在私钥不泄漏的前提下不可利用；但这意味着一旦签名密钥泄漏（或未来换成多渠道多密钥），一个带 `../../` 或 `x -> /Users/...` 符号链接的 tar 就能在 `web-dev` 之外落文件。属于纵深防御缺口，不是现行可绕过的验签漏洞（我另外用内置公钥对线上 manifest 做了验签，`verify: true`）。

15. **轻** · `macos/Sources/Rhodeside/PetManager.swift:352-354` + `SettingsController.swift:83-87`
    设置窗口刚关闭又立刻打开时，会复用一个已经 `removeAllScriptMessageHandlers()` 的页面。
    `windowWillClose` 同步移除消息处理器，而 `settingsClosed()` 是 `DispatchQueue.main.async { self?.settings = nil }`；如果 `openSettings()` 在这个 async 之前被调用（例如 `applicationShouldHandleReopen` 在关窗事件同一轮触发），`settings` 仍非 nil，`show()` 会把旧窗口再显示出来，随后 async 把它置 nil 释放——用户看到窗口一闪就没了，且那一小段时间里页面消息不通。建议在 `windowWillClose` 里同步把 `manager.settings` 置 nil（用 flag 防重入），不要延迟。

16. **轻** · `macos/Sources/Rhodeside/ModelLibrary.swift:59-63, 23-32`
    `delete(_:)`/`find(_:)` 直接用 `appendingPathComponent(name)`，不校验 `name`。`deleteModel` 消息里的 `name` 正常来自 `ModelLibrary.all()` 的目录名（不含 `/`），但配置/消息若被手改或伪造，`name = ".."` 会让 `dir` 指到 `Application Support/Rhodeside` 的父目录并通过 `isDirectory` 检查，`trashItem` 会把它移进废纸篓。`SchemeHandler.resolve` 已经挡了 `..`，`ModelLibrary` 自己没有，属于不一致的输入校验。

总评：骨架、Swift↔TS 消息契约和 Ed25519 热更新链本身是自洽的（线上清单验签通过、字段与 tar 内容一致，未发现可绕过的验签路径或必崩点），真正的问题集中在热更新失败分支的状态机（失败被 ETag 缓存、错误被 304 抹掉）、部署脚本的错误传播（远端 zsh 管道吞掉 `swift test` 失败、发布先于编译），以及设置页用旧 `group`/旧 `model` 拼 patch 导致的「Select 值不在选项里、界面与实际不一致」。
