## 高

### H1. 引导页一旦进入「已登录」就没有出口：模型拿不到时会一直卡着
- 位置：`web/src/welcome/Welcome.tsx:31`、`:48-66`
- 触发场景：已登录（`auth.phase === 'signedIn'`），但下面任何一种情况出现：
  1. 拿不到目录。比如 `/v1/ticket` 返回 502（Priestess 不可用），或者返回非 `app_access_denied` 的 401/403
     （`ticketBlockedUntil` 会让它停 5 分钟），或者 `models.json` 返回 404（`catalog = nil`）、返回 5xx、验签失败。
     这时 `catalog` 为空，页面一直停在「正在获取模型列表…」。
  2. 下载一直失败。退避时间是 30s → 2m → 8m → … → 1h，页面上一直显示「下载失败，稍后自动重试」。
  3. 同名导入模型挡住了下载（见 L4）。这时 `state` 永远是 `available`，页面一直显示「下载中…」。
- 为什么错：这个分支的 footer 只有 `<Button disabled={!done}>开始使用</Button>`，**没有「跳过」**。
  页面也不显示 `state.updates.error`，用户看不到原因。唯一的出路是点红叉关窗，但关窗不会调 `finishOnboarding`，
  `onboarded` 仍是 false，所以每次启动（包括开机自启）都会再弹出来。
- 建议修法：已登录分支也在右下角放一个「稍后 / 跳过」（调 `finishOnboarding`）。`catalog` 为空或有 `updates.error` 时
  把错误显示出来。另外可以考虑：登录成功就算完成引导，下载进度留给设置页显示。

- 证据：`curl http://127.0.0.1:8066/models/荒芜拉普兰德/defaultskin/front/char_1038_whitw2.skel`
  返回 `200 784211`，`/models/index.json` 里也有这个模型。进程是 pid 2953522 的 vite，监听 `0.0.0.0:8066`。
  cloudflared 没有把 8066 映射出去，所以公网拿不到；但 **局域网 / tailnet 上的任何设备都能直接下载**。
- 另外，只有 deploy.sh 的 `--exclude=./models` / `rsync --exclude /models` 把模型挡在包外。只要走一次 SpineStage 自己的
  `vite build`（输出到 `web/dist`，比如以后部署 SpineStage 页面），vite 就会把 `public/models/荒芜拉普兰德` 连同

  同时从 `public/models/index.json` 里删掉这一条。dev server 如果只需要本机访问，改成监听 127.0.0.1；
  如果开发时确实要用这个模型，就用一个不进 public 的中间件，并加访问控制。

### MH2. 旧版 App 在 ENFORCE=1 之后收不到这次更新（迁移断档）
- 位置：`/opt/stacks/rhodeside/compose.yaml`（`ENFORCE: "1"`）和 `nginx.conf:43-56`；对照旧 App 的逻辑。
- 证据：旧包 `Rhodeside-1790695603482.tar.gz` 的 settings 前端里有开关「使用 Priestess 登录更新通道」
  （`checked: n.enabled`），`AuthConfig.enabled` 默认 false；旧的 `ticketHeaders` 在 `!auth.enabled` 时不带票据。
  005 报告第 9 行记录的当时状态是 `ENFORCE=0`。
- 触发场景：任何没有手动打开这个开关并登录的旧版用户，`app.json` 都会一直 401，
  只能看到「更新通道需要登录（设置 → 账号）」，永远自动更新不到新版本。
- 建议修法：二选一。一是过渡期让 `app.json` 和 `v1/apps/`（不含模型）不做 auth_request，只把 `models` 设为强制鉴权；
  二是明确通知旧用户手动开开关并登录。App 包本身已经不含授权模型，放开 App 通道不影响授权要求。

## 中

### M1. 模型出新版本后，正在用它的桌宠不会重新载入
- 位置：`macos/Sources/Rhodeside/Pet.swift:137-139`（`modelFilesMaybeChanged` 只比较文件名列表）；
  `PetManager.swift:350-353`
- 触发场景：服务器上的模型内容变了，但文件名没变（最常见的就是修贴图或 skel），`version` 哈希随之改变。
  App 下载后原子替换了 `models/荒芜拉普兰德`，接着调用 `onModelsChanged`。这时 `find(model).files == loadedFiles`，
  所以不会调 `sendLoad`。
- 为什么错：状态变成了「已下载」，但桌面上还是旧版本，要等重启或者换一次时装才会更新。
- 建议修法：`ModelStore.install` 成功后把装好的模型名传给 `onModelsChanged`，对 `config.model == name`
  或回退到它的桌宠强制调 `sendLoad`。也可以在比较时带上版本号或 mtime。

### M2. 「outdated」可能永远不更新，UI 却写着「稍后自动更新」，而且没有按钮
- 位置：`ModelStore.swift:100-102`（`want` 要求被桌宠使用、default 或 requested 之一）；
  `Settings.tsx:36-37`（`outdated: '有新版本，稍后自动更新'`）、`:318`（只有 available/failed 才有「下载」按钮）
- 触发场景：一个非 default 的在线模型当初是因为有桌宠在用才自动装上的（不在 requested 里）。后来桌宠换了别的模型，
  或者服务器把某个已装模型的 `default` 改成了 false。之后出新版本时 `wanted` 返回 false，
  状态停在 outdated，设置页也没有任何办法触发更新。
- 建议修法：`wanted` 对「已装在线模型且版本不同」直接返回 true（没被 dismissed 就更新）。
  或者 install 时把 id 加进 requested。或者给 outdated 也加一个「更新」按钮（发 `downloadModel`）。

### M3. 删掉正在使用的默认在线模型后，桌宠继续显示已删除的模型，提示也不对
- 位置：`SettingsController.swift:185-198`；`Pet.swift:112-123`
- 触发场景：设置页删除「荒芜拉普兰德」，而桌宠正在用它。删除代码把桌宠改回 `builtinModel`，也就是同一个模型，
  只是 outfit/group 被改了，于是走 `update` → `sendLoad`。`find` 找不到这个模型，函数提前 return，
  但**网页里已经画着的旧模型没有清掉**，`info` 也不为 nil，所以桌宠照样显示。重启之后又不显示了，前后不一致。
  同时 `lastError` 写的是「登录 Priestess 后会自动下载」，但这个模型已经进了 dismissed，**不会**自动下载。
- 建议修法：`sendLoad` 找不到模型时给网页发 unload（或者重新 `loadPage`），把 `info` 置 nil 并隐藏桌宠，
  `loadedFiles` 也置空。提示文字要区分 dismissed（「已删除，可在设置 → 模型重新下载」）和还没下载两种情况。

### M4. 退出登录（或换账号）后，最长 10 分钟内仍然用旧票据下载
- 位置：`RemoteUpdater.swift:426`（`ticket` 缓存）；`Auth.logout()`（`Auth.swift:143-151`）不会通知 updater 清掉票据
- 触发场景：退出登录后，`PetManager` 的 `auth.onChange` 调 `updater.check()`，而 `ticketHeaders` 看到
  `ticket.expires > 60s` 就直接用缓存。这样在剩下的有效期里，仍然会拉 App、前端和模型的更新（包括新模型）。
  如果换成一个没有权限的账号登录，也会继续用上一个账号的票据。
- 为什么错：违反了「只有登录用户能下载」。影响窗口不长，但确实存在。
- 建议修法：updater 记住 auth 的 phase 或 user，变了就 `ticket = nil`。也可以在 `auth.onChange` 里先调
  `updater.resetTicket()` 再 `check()`。

### M5. publish.mjs 的模型版本号不包含模型名：改名后会复用旧包，App 永远装不上
- 位置：`macos/scripts/publish.mjs:98-103`（hash 只包含相对路径和文件内容）、`:108`（包内顶层目录是 `m.name`）；
  `ModelStore.swift:117`（`top == [m.name]`）
- 触发场景：在 `macos/models.json` 里只改 `name`，文件不动。`version` 不变，所以 `${id}-${version}.tar.gz` 已经存在，
  不会重新打包；包里的顶层目录仍是旧名字。签名目录里写的却是新名字，App 解压后校验失败，
  报「模型包内容不对」，并且一直退避重试。
- 建议修法：把 `m.name` 也放进 hash（例如先 `h.update(m.name + '\0')`），或者打包前检查已有包的顶层目录名。

## 低

### L1. 服务器上的旧 App 包里还带着授权模型
- 证据：`/opt/stacks/rhodeside/data/v1/apps/` 下 5 个包中有 4 个（1790694642987、1790694768144、1790694811538、
  1790695603482）含 `Rhodeside.app/Contents/Resources/models/荒芜拉普兰德/…`（每个 28 条）。
- 说明：这些包都要票据才能下载，受众和模型本身相同，所以不算越权；但和「不再打进 App」的目标不一致。
  `publish.mjs` 只对 models 做了「删掉不再引用的旧包」，App 包按 `keep: 5` 保留。
- 建议：手动删掉这 4 个旧包，或者发布时丢掉 Resources/models 非空的旧 App 包。

### L2. 目录变化本身不会推送状态，设置页 / 引导页的 catalog 可能是旧的
- 位置：`RemoteUpdater.swift:140-142`（defer 只比较 lastError/remoteWeb/remoteApp/appState）、`:232`
- 触发场景：已登录且没有报错，服务器新增一个非 default 模型（`wanted` 为空，不会下载，也不会调 onChange），
  或者目录从 404 变成有内容。这时设置页看不到新模型，要等别的事件触发推送才会刷新。
- 修法：`catalog` 的内容（build）变化时调一次 `onChange`。

### L3. 下载期间导入同名模型，导入的模型会被覆盖并永久删除
- 位置：`ModelStore.swift:120-130`（先把 dest 挪到 `.old` 再 `removeItem`，不经过废纸篓）；
  `Importer.swift:49`（`uniqueName` 只看磁盘，不考虑正在下载的在线模型）
- 触发场景：首次登录后正在下载「荒芜拉普兰德」，这时用户导入一个同名文件夹。`wanted` 在下载前检查过 `isUserModel`，
  install 时不再检查，于是用户导入的内容被挪走后直接删除。
- 修法：install 前重新检查一次：dest 已存在但 `installed()[name]` 为 nil，说明那是用户自己的模型，放弃安装。

### L4. 有同名的导入模型时，在线模型永远是 available，点「下载」没有任何反应
- 位置：`ModelStore.swift:104`、`:140-142`
- 触发场景：`models/荒芜拉普兰德` 是用户手动放进去或导入的，不在 installed 记录里。`status` 显示 available，
  点下载只会把 id 加进 requested，`wanted` 仍然返回 false，页面没有任何提示。这也会导致 H1 的卡死。
- 修法：`status` 对这种情况单独给一个 `conflict` 状态，并在 UI 上说明原因。

### L5. 模型缺失时 `loadedFiles` 没有清空，之后 models 目录的每个事件都会重复 sendLoad
- 位置：`Pet.swift:118-123`、`:137-138`
- 触发场景：模型没有下载，也没有内置模型可回退。`find(...)?.files`（nil）永远 `!= loadedFiles`（`[]`），
  所以 models 目录的每个 FSEvents 事件都会再调一次 `sendLoad`：写一条 info 日志，再 `petChanged` 推一次状态。
  另一种情况：桌宠回退到了内置模型，此时 `loadedFiles` 是内置模型的文件，`config.model` 的文件列表（nil）
  和它不相等，于是任何模型目录变化（比如导入别的模型）都会把内置模型重新载入一遍。
- 修法：用「当前实际载入的模型名 + 文件列表」来比较。

### L6. `modelDeleted` 在真正删除之前就清掉了记录
- 位置：`SettingsController.swift:188-189`
- 触发场景：`trashItem` 失败（权限问题、废纸篓不可用）。installed 记录已经删了、已经进了 dismissed，
  但目录还在，之后它就被当成导入模型（见 L4），状态无法恢复。
- 修法：先 `ModelLibrary.delete`，成功后再调 `ModelStore.modelDeleted`。

### L7. `ModelStore.verify` 没有校验 `id`，而 id 会直接拼进路径
- 位置：`ModelStore.swift:43-47`；id 用在 `:113`、`:121`（`updates/model-<id>`）和下载文件名
  `RemoteUpdater.swift:245,404`
- 说明：目录有签名，这条只是纵深防御层面的缺口；路径和名字都校验了，唯独 id 没有。
  建议按 publish 端同样的规则 `^[a-z0-9-]+$` 校验，并拒绝重复的 id 或 name。

### L8. 小问题
- `Auth.swift:12`：`Phase` 里仍然有 `disabled`（任务说明说已经去掉了）；`bridge.ts:50` 和 `Settings.tsx` 的
  `AUTH_PHASE` 也还留着。不影响功能。
- `Config.swift:78-81`：config.json 损坏时会退回 `AppConfig()`，`onboarded` 变成 false，已经在用的老用户会再次看到引导页。
  可以在 `.broken` 分支里把 `onboarded` 设成 true。
